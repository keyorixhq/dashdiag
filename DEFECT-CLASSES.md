# DashDiag defect-class derivation

Research pass, no code changes, no checks run. Derives a ranked list of defect
classes for DashDiag from first principles, using the method that produced the
Keyorix (sibling project, secrets server) review list: (1) what ambient state
does the process inherit and never normalise, and (2) what does the product
claim, and what would falsify the claim silently. Keyorix's list is not reused
— about half of it (row scoping, audit-write failure, DB constraints, RBAC
oracles) assumes a multi-tenant server with a database and an authorization
model, which DashDiag is not. See "Exclusions" at the end for the explicit
disposition of each.

All citations are `file:line` against `~/proj/dashdiag` as of 2026-08-31.

### Ambient state (the process's own environment, distinct from subprocess hardening above)

| Signal | Normalised, or silently inherited? |
|---|---|
| **Timezone** | **Silently inherited — confirmed risk.** `internal/collectors/timeline_linux.go:448` parses `dmesg -T` output with `time.Parse("Mon Jan  2 15:04:05 2006", timeStr)`. `dmesg -T` prints in the *system's local time* (via libc `localtime()`), but Go's `time.Parse` with no zone token in the layout defaults the resulting `time.Time`'s location to **UTC**. The digits are local, the label says UTC — so `.Unix()` (`:492`) is off by the host's UTC offset. `journalctl --output=json` events (`:151,164`) use `__REALTIME_TIMESTAMP`, real epoch microseconds, immune to this. Both event streams are merged into one timeline: sorted by `TimestampUnix` (`:81-84`) and deduplicated by `minuteUnix := TimestampUnix / 60` (`:318`). On any non-UTC host, dmesg- and journalctl-sourced events for the *same real incident* land at different absolute instants — ordering and same-minute dedup break silently, with no error and nothing a UTC CI box would ever surface. `HardenedEnv` (`trustedexec.go:18-27`) pins locale for subprocess parsing but deliberately does not pin `TZ`. |
| **Working directory** | Normalised almost everywhere — home-anchored writes (`store/jsonl.go:62-79`, `init/firstrun.go:12-27`, `config/config.go:145-166`) explicitly refuse to fall back to a CWD-relative path if `$HOME` can't be resolved, with comments citing exactly this risk. One documented exception: `cmd/hook.go:222-231` (`dsd hook install`) requires CWD to literally be the git repo root (checks `.git` via `os.Stat`, no walk-up) and **fails loudly** if it isn't — not silent, but a real "must be run from repo root" assumption with no test enforcing it. |
| **umask** | **Silently inherited — confirmed risk.** No `syscall.Umask` call anywhere in production code. All `~/.dsd/*` writes pass explicit mode bits (`0600`/`0750`), but those are ANDed with the calling process's inherited umask per POSIX/Go semantics. A permissive host umask (`0000` — some container base images, some root cron setups) would leave `~/.dsd/*` more open than the code intends, and dashdiag never pins this itself. |
| **TMPDIR** | **Silently inherited for one path.** `internal/source/tarball.go:30,54` (`dsd capture --raw` staging) calls `os.MkdirTemp("", "dsd-raw-*")` — empty dir argument, so it resolves via `$TMPDIR`/`os.TempDir()`. No validation of what `$TMPDIR` points to (full disk, FUSE/network mount, world-writable dir) — failure surfaces only as whatever raw OS error `MkdirTemp`/write returns. Baseline writes (`baseline.go:124,142`, `golden.go:45`) are unaffected — they pass an explicit home-anchored `dir`. |
| **Locale (own process)** | Not a risk. No `golang.org/x/text` dependency anywhere in `go.mod`; all string case-folding operates on ASCII tokens dashdiag controls or subprocess output already pinned to `LC_ALL=C` by `HardenedEnv`. |
| **TERM / output width** | Not applicable. No `$TERM`, `$COLUMNS`, or `golang.org/x/term` usage anywhere; `internal/output/tty.go:94-100` only checks whether stderr is a character device to pick human vs. plain mode. No width-dependent rendering exists to be garbled. |
| **HOME** | Normalised, fails closed. `os.UserHomeDir()` errors (no silent fallback) when `$HOME` is unset; every call site (`jsonl.go:74-77`, `firstrun.go:13-23`, `config.go:151-166`, `tips/state.go:40`) handles that explicitly rather than defaulting to CWD or `/root`. |
| **HOME preserved across privilege change** | **Silently inherited — confirmed risk, different mechanism than "HOME unset."** No `os.Chown` anywhere in production code. If dashdiag runs as root with `$HOME` still pointing at a normal user's home (`sudo -E`, `su` without `-`, some non-standard sudo configs that don't reset the environment), `~/.dsd/state.json`, `store.jsonl`, and baseline files are created **root-owned**, mode `0600`/`0750`, with nothing to chown them back. A later unprivileged run by that user then fails to read/append its own history — silently, since the failure looks like "first run" or a quiet `EACCES` depending on the call site, not a labelled ownership error. Default `sudo` (which resets `$HOME` via `env_reset`) avoids this by accident, not by dashdiag's own design. |

## Task 2/3 — derived classes (confirmed) and Task 3 candidates (confirmed/discarded)

Each class states: mechanism, why it's invisible today, the probe that would settle it, and the consequence if real.

### C1 — Exit code conflates "tool failed" with "host is fine" and with "host is critical"

- **Mechanism:** `exitCodeFromInsights` (`render/health.go:1736-1749`) reads only `insight.Level`. `JSONCounts.Errored` is computed (`json.go:41-55`) but never fed into the exit path. `rootCmd.Execute()` errors map to exit 1 (`root.go:204-207`); an unrecovered panic (no `recover()` in `runner/*.go`) maps to exit 2 by Go's default. Three distinct failure modes — real WARN, real CRIT, and "the tool didn't actually check anything" — collapse onto the same two non-zero codes, and total collector failure collapses onto **0**, the "healthy" code.
- **Why invisible today:** CI and the project's own smoke tests (`scripts/smoke-test.sh:25`, `scripts/hardware-smoke.sh:134-139`) assert `exit code in {0,1,2}` as success, which is true by construction and can never fail this way. Nothing in the test suite runs dashdiag in a state where all collectors error and checks that the exit code differs from a clean run.
- **Probe:** force every collector to return an error (e.g. run against a chroot/container with `/proc` and `/sys` unmounted or replaced with empty stubs, or monkey-patch the runner in a test to inject `Err` on every result) and assert the exit code is **not** 0 and JSON output surfaces it unambiguously. A second probe: inject a deliberate panic in one collector goroutine and confirm the process doesn't crash the whole run (today it does, per no-recover finding).
- **Consequence if real:** exactly the failure mode the product exists to prevent — "a report that says healthy when something is broken is worse than a tool that fails to run" (from the task brief) applies to dashdiag's own control-plane signal, not just to what it reports about the host. Any CI/automation keying off exit code cannot tell "go check your monitoring pipeline" from "the target host is on fire."

### C2 — `/dev/kmsg` degrade signal is an euid proxy, not a read-result sentinel

- **Mechanism:** `readKmsgLive` (`logs_linux.go:178-200`) swallows the `os.OpenFile` error and returns `""`. The only downstream caveat, `NeedsRoot = true` (`:72-74`), fires purely on `os.Getuid() != 0` — it does not know whether the read actually failed.
- **Why invisible today:** it's the exact bug shape the project has already found once (VMware vNVMe, non-root run silently OK) but in a place where the *documented* fix pattern (euid-gated caveat) is present and looks correct at a glance — the gap is narrower: a root run in an environment that restricts `/dev/kmsg` by another mechanism (container seccomp profile, LSM policy, a hardened kernel) than uid.
- **Probe:** run dashdiag as root inside a container/profile that denies `/dev/kmsg` specifically (e.g. a seccomp profile blocking the `syslog`/`ioctl` calls needed, or a bind-mount that hides it) and confirm `OOMKills`/`Segfaults` still show a caveat instead of a bare `0`.
- **Consequence if real:** false-negative OOM/segfault detection under exactly the kind of hardened-container host dashdiag is increasingly deployed into (k3s, gVisor-adjacent setups) — silent, no distinguishing field in the JSON output.

### C3 — Timezone-naive cross-source event correlation (dmesg vs. journalctl)

- **Mechanism:** `dmesg -T` output (local time, no zone info) parsed with a UTC-defaulting `time.Parse` (`timeline_linux.go:448`) is merged and deduplicated (`:81-84,318`) against `journalctl`'s real epoch timestamps.
- **Why invisible today:** this is the textbook ambient-state class from the method brief — correct on a UTC dev machine and in UTC CI, wrong on any non-UTC customer host, and produces no error. A CI box that's UTC (the default for most CI images) will never exercise the skew.
- **Probe:** set `TZ=America/Los_Angeles` (or any non-UTC zone), trigger a kernel event and a matching journald log entry for the same real incident (a synthetic OOM kill is enough), run `dsd health deep` or the timeline collector's unit tests with that TZ, and check whether the two records land in the same dedup minute / correct relative order.
- **Consequence if real:** wrong ordering or a broken same-minute dedup in exactly the feature (kernel-timeline correlation) whose entire value proposition is "these two things happened together." A wrong correlation is a confident wrong answer, not an absence of one.

### C4 — Ambient umask/TMPDIR/PATH inheritance changes on-disk permissions and tool resolution between hosts

- **Mechanism:** three independent inheritance points, same root cause (unpinned ambient state), grouped as one class because the probe and fix shape are the same:
  - umask: explicit `0600`/`0750` mode bits are ANDed with the inherited umask; nothing calls `syscall.Umask` to pin it.
  - `$TMPDIR`: `capture --raw` staging (`tarball.go:30,54`) uses the default temp dir.
  - `$PATH`/tool resolution: `internal/cvedata/rpm.go:18` and `internal/platform/profile.go:408` bypass `source.ResolveTrustedTool`, the project's own defense against PATH-based tool substitution, and inherit `$PATH` as-is; those same two sites also bypass `HardenedEnv`'s locale pin (`oval_debian.go:340-341` too).
- **Why invisible today:** correct on the developer's shell (sane umask, sane `$TMPDIR`, sane `$PATH`) and in CI (same), wrong only on a host where any of these differ — a root cron job with `umask 0000`, a container image with `$TMPDIR` on an unusual mount, a host with a shadowed `rpm`/`systemctl` earlier in `$PATH`.
- **Probe:** run with `umask 000` and check the actual mode of a freshly created `~/.dsd/state.json` (`stat -c %a`) against the intended `0600`. Run with `TMPDIR=/some/read-only-or-full/path` and check that `dsd capture --raw` fails with a clear, attributable error rather than a bare OS error. Run with a `$PATH` that puts a fake `rpm`/`systemctl` first and confirm `internal/cvedata/rpm.go` and `internal/platform/profile.go` still resolve the real trusted binary (they currently would not).
- **Consequence if real:** `~/.dsd/*` (which can carry SUID paths and process listings, per the project's own `--out` comment) ends up more permissive than the code's stated intent; `dsd cve` (rpm path) could silently read/execute a substituted `rpm`/`systemctl` if one is placed earlier on `$PATH` and the invoking user (often root) is tricked into a bad `$PATH` — the exact class `ResolveTrustedTool` exists to close, just not closed everywhere.

### C5 — Documented "write only to `~/.dsd/`" invariant is not actually true

- **Mechanism:** `cmd/inventory.go:95` (0644, world-readable, arbitrary `--out` path), `cmd/hook.go` (shell RC files, a repo-relative script, a git hook, a systemd unit pair, a GitHub Actions workflow) all write outside `~/.dsd/`.
- **Why invisible today:** each site is deliberate and commented, so it reads as "intentional and safe" to whoever wrote it — but the invariant as stated in CLAUDE.md has no documented carve-out, so nothing stops a future collector or command from reusing the "well, `hook.go` already does this" precedent for something less carefully justified. `cmd/inventory.go:95` is the one that combines "outside `~/.dsd/`" with "permissive mode on a payload whose sensitivity is a judgment call."
- **Probe:** not a runtime probe — a documentation/policy reconciliation. Either narrow the CLAUDE.md rule to name its actual exceptions (self-installed hooks, exported reports) or move `cmd/inventory.go`'s default `--out` behavior to match `--out` elsewhere (0600) and require an explicit `--world-readable`-style opt-in for the current 0644 default.
- **Consequence if real:** low technical severity (this is host inventory data, not credentials, and the write requires the operator to pass `--out` deliberately) but it is the kind of quiet contract drift that turns into a real leak once a less-careful collector is added under the same precedent.

### C6 — Redaction is explicitly best-effort but is the only thing standing between a shared bundle and a leaked secret

- **Confirmed as a real class** (Task 3 candidate #1). `internal/source/sanitize.go:15` self-documents as "not a guarantee." `--identifiers` explicitly excludes IPv6 and disk serials. The pattern-based approach (regex over `key=value`/`key: value` shapes, PEM headers, AWS key prefixes) will miss anything that doesn't match those shapes — a credential embedded in a URL query string, a token in an unusual env var name picked up by the generic passthrough (`fsaccess.go:55`), a secret baked into a config file consumed via `--policy`/`--oval` and echoed back into a raw collector field.
- **Probe:** plant a distinct, greppable fake credential in each of: an env var with a non-matching name (e.g. `MY_APP_SECRET_VALUE=canary123`), a `--policy` YAML file, a file under a path a collector walks (e.g. a fake `.pgpass`-shaped file if any collector reads dotfiles), and a URL-embedded token in a config value a network collector might log. Run `dsd capture --raw --sanitize --identifiers` and grep the resulting tarball for the canary string.
- **Consequence if real:** exactly the scenario the product's own `PRIVACY.md`/`SECURITY.md` exist to prevent — a bundle explicitly designed to be attached to a support ticket or sent to a vendor carries a credential through.

## Task 3 — remaining candidates, confirmed or discarded

| Candidate | Verdict | Basis |
|---|---|---|
| Redaction gap in shared bundles | **Confirmed** — folded into C6 above. |
| Untrusted archive extraction (tar-slip / zip-slip on `capture`/`decode`/`compare` input) | **Discarded — already mitigated.** `internal/source/tarball.go:169-184` (`untarGzWithLimits`) rejects any entry whose cleaned path starts with `..` or is absolute, caps entry count, caps per-file and total extracted size, and skips all non-regular-file entries (so symlink-based traversal is closed too, not just `..`-based). Confirmed by direct reading, not by report. |

### Exclusions — sibling-project classes that don't apply here

- **Multi-tenant row scoping** — DashDiag has no tenants, no rows, no database. There is nothing to scope. Not a "small version of the same risk," genuinely inapplicable — DashDiag's entire persistent state is one operator's `~/.dsd/` directory.
- **Audit-write failure (write to audit log fails silently, action proceeds anyway)** — DashDiag performs no actions that need auditing; it is read-only by design (confirmed under Mutation above). There is no "action" whose audit trail could go missing.
- **Database constraints (as a correctness backstop)** — no database. The nearest analogue, atomic `~/.dsd/*` writes via temp-file-then-rename, was checked directly (Outputs table) and holds.
- **RBAC oracles (does an authorization check correctly deny)** — DashDiag has no authorization model; the only "access control" that exists is the host OS's own file permissions and root/non-root distinction, which is exactly what C2 and C4's ownership/degrade findings already cover under a DashDiag-native framing rather than an RBAC one.

### Real, but not worth sweeping now

- **Exhaustive version-drift audit across all ~60 external-tool parsers, beyond what the 99-collector sweep already covered.** Updated after the follow-up pass: the "does an unrecognised format error or silently read as healthy" question was checked for a shared entry point that would collapse it to one review — there isn't one, so the sweep already did the only version of this question that's actually askable, at full breadth (99 collectors, not a 3-collector sample), and found 26 real gaps (2 now fixed, 24 ranked in `COLLECTOR-SWEEP.md`).
